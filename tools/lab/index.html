      About this view

      Single-value consensus

      Reading the grid

      Each dot is a node, colored by its current value (colors repeat past 7 values — a distinct init reads as noise early; order emerging IS the protocol working). Gray = ⊥. Red ring = blocked. Click a node for its sample edges (teal out, magenta in). Keys: ← → step, space = play. Click the timeline to move the grid to that round.

      The engine

      Rust simulator compiled to WASM — identical engine, RNG, and trace schema as the CLI, so seeds are canonical and reproducible: cargo run --example trace -- out.json n seed beta gives byte-identical traces. Targets (sample edges) are recorded only for n ≤ 2000 to bound trace size.

      Timeline lanes

      Value composition: the share of nodes per value over the rounds, ⊥ in gray on top, and a red strip for the share blocked. Per-node timeline: one row per node, grouped by initial value; with more nodes than rows it shows every k-th node and says so. A red notch marks a blocked node. The readout gives the numbers for the round under the cursor, and its status says whether every holder agrees on one value, nobody holds a value, or neither.

      Blocking strategies

      Fresh, sticky + background and a scheduled program run in a live session: the live path draws exactly the stream the batch engine draws for them. Permanent and the adaptive strategies need draws or node state the live path does not have, so they run through the batch engine and open as a finished run, which is the exact run the engine gives for that spec and seed. The 0-late adversary reads the state one round later than Definition 1.1 allows and is outside the paper’s model; the α-late adversary is Definition 1.1, and α = 1 is the 1-late adversary.

      Sticky + background

      The slider drives a persistent targeted set; the blocked % in the form adds never-stopping background noise under it.

      Setup form

      Commit T (compact)

      A command executes once aged T rounds. Safety needs T > T_B + max(T_B, T_M), so scale T with log₂n: a too-small T gives live commitment errors, visible in the safety flag.

      Window T and the broadcast-time floor

      The checkpoint clock: every T rounds the aged prefix is executed and a new checkpoint minted, or a reset-armed server rolls back to the last one. Below the broadcast-time floor T_B the system cannot re-converge at all (cliff preset).

      Window T — why it matters

      Why T is the single knob that decides whether a surged system ever comes back.

      What the length of one checkpoint window — commit clock and rollback granularity in one.

      Data spec proto.t_window_rounds; the clock chip reads it back from the run.

      §5 certificates over recovery

      Why §6 p. 30 claims the §5 certificate layer carries over to Alg 6 in one sentence and never constructs it; Theorem 6 is proved for the compact protocol only. This is the thesis's construction, not the paper's.

      What certificate state lives inside each checkpoint, so rollback restores it and adoption clones it with no new propagation path, and commands are attested only once a boundary has fully executed them (Lemma 6.9) — never while they sit revocable in P. Clients then run §5's client protocol verbatim (p. 25), resending until a contacted server acknowledges.

      Data certs_json over the servers' checkpoint-resident forests; off by default because the ack-tied client changes the client-stage draw pattern.

      Scenario presets

      Why the headline results need a specific stimulus shape, and hand-driving the slider is fiddly.

      What a form prefill plus a scheduled blocking program (round segments, each with a blocked fraction) that drives the live slider for you — surge → release replays the release law's regime (full blackout ending inside a window), partial surge blocks 30% and heals without the spiral, cliff runs T below the broadcast-time floor until the engine aborts.

      Data pure JS — the run still records its actual per-round fractions, so the export replays exactly what happened.

      Servers

      R-state grid

      Why whether a server will roll back at the next boundary is decided by R, and R is NOT readable off its log — a reset-armed server can still hold one.

      What teal = no-reset (safe) · amber = reset (will roll back) · grey = ⊥. Lines flash the peer that caused a change: teal = whose checkpoint was adopted, amber = whose reply cleared the reset. Pink ring = blocked by the schedule, dashed ring = blocked by you (⌖ — a surgical adversary instead of the slider's random one). The reset wave literally spreads by gossip; the flashes show the carriers.

      Data the r field on each node glance, plus the step payload's edge lists.

      Pinning one server

      Why a rollback is invisible in aggregate counts; you have to watch ONE server lose its history and rebuild it.

      What the pinned server's R, log and executed lengths, its checkpoint window and |P|, and two hashes — its current executed sequence against the one its checkpoint holds, Lemma 6.7's identity check by eye. They diverge while it runs ahead and re-converge when a boundary commits or a rollback resets it. Time travel does not apply here: the engine keeps no per-node history, so this is live state only.

      Data node_detail, fetched on demand and re-fetched each round while pinned.

      Readout under the timeline

      Window clock

      Why everything in Alg 6 happens on the window clock — commits, checkpoints and rollbacks all land on boundaries.

      What the current window [a,b), its length T, and the rounds left to the next boundary. Once a release has been seen it also carries r* (the recovered round) and R = r* − release.

      Data recovery rows' window field plus the spec's T.

      Recovery phase

      Why a recovery claim is only meaningful once the surge has actually ended — on a calm run there is nothing to recover from.

      What PROVISIONAL from the first release (fewer than n/4 servers unblocked → n/4 or more) until a clean converged suffix confirms it; CONFIRMED after. r* is suffix-universal — a relapse voids a provisional candidate, which is why the chip refuses to commit early.

      Data the recorded β track plus the same scan the engine's recovered_round uses.

      Block drawer: chain, forest, certificates

      Whole forest (compact)

      Blocks = committed commands (newest right, dashed slot = next commit). The Merkle forest hangs from the blocks — scroll to follow it; a client row click highlights its tree path. Large m switches to the skyline (one bar per bit of m).

      Whole forest (recovery)

      Why Alg 6 commits in lumps at window boundaries, and what it commits is a real sequence with real hashes — the blockchain the protocol actually builds. Watching it grow makes "committed" concrete, and the merge cascade shows a whole batch being absorbed at once.

      What one block per committed entry (newest right, dashed slot = the next commit), labelled with the command occupying it; the trees hanging below are the Merkle forest over those blocks — heights, ranges and root hashes come from the engine, no interior hash is invented. A boundary commit flashes the carry chain as equal-height trees merge; past 2^7 leaves the forest gives way to the skyline (one bar per bit of m). Click a block to pin its command on the charts. Empty stretches are honest: nothing commits between boundaries.

      Data chain_json over the canonical committed sequence — the longest executed prefix in the population, the longest executed sequence among the n servers, a display construct rather than any one server's S_i. While prefix consistency holds it extends every server's S_i (Lemma 6.9); a prefix violation freezes the panel, and per-server retractions of executed commands (Def 1.5) are counted in the run report, not redrawn here. Without certificates this is structure only; with certificates on (the thesis's RQ11 construction, not the paper's) the drawer also lists client certificates and verifies them.

      Verify everywhere

      Verify every issued certificate against every server's forest (Thm 6): tally = accepted/covered, stamped with the round it was computed at. On demand — re-click to refresh.

      Lifelines margin

      Deadline: the round the whole committed prefix through an entry is T rounds old, the earliest it can execute (running max of the stamps from position 1, plus T; a bracket spans the range when accepted resends restamped it; entries without a known stamp are left out, so deadlines are lower bounds). Both protocols show the margin: deadline − position fixed; below 0 the entry aged before it was fixed. Below T/4: tight. Recovery row hovers add the slack to checkpoint: the earliest checkpoint that could freeze the entry (the first window end at or after the deadline) − position fixed, since recovery freezes P only at window ends; the entry may in fact be frozen at a later checkpoint, so the slack measures to the earliest possible one. The selected command's row is white.

      Canonical spill viewer

      What a spill is

      Why a lean recovery run has its servers forget their committed prefix — that is the whole point, and it is what takes a big dispatch from ~15 GB to single-digit GB. Nothing in the run then holds the committed history any more, so the chain panel below cannot be fed from a server. The spill is the one canonical record of that history: the committed stream, plus every server's forget offset and executed length at every T-window boundary.

      What pick a boundary and a server; the chain panel renders that server's committed view, reconstructed from the stream and checked against the digest chain the run itself recorded — not trusted. Parse, reconstruction and verification all happen in the same Rust reader the run's own diagnosis path uses; the browser only reads the file and draws.

      Data .runs/spills/*.jsonl, written once per boundary by the observer just before the servers forget.

      Timeline lanes

      Safety checks

      The indicator next to the timeline title reads "✓ 7 passed", or "✕ 2 failed · 5 not applicable" when something failed; its hover lists every check. When a check failed, clicking it opens a card: each failed check with its first round, one line of evidence and a jump to that round; the not-applicable checks (vacuous: nothing executed yet, so they cannot fail) and the passing ones folded into one line each; and how the run ended, which is a status, not a check. The checks: no fork (safety_ok: every executed sequence is a prefix of one order; not Def 1.4 nor Def 1.5), monotone (Def 1.5: no server retracts an executed entry), useful in step (Def 1.4 read at every round end; a lag count, since one useful server a commit behind counts too), in step at window ends (Def 1.4 after the pass, the instant Lemma 6.7 speaks about), checkpoint lineage (fork_ok, Lemma 6.5/6.7; its round is the first with cp_fork_k > 1), committed checkpoints (commit_fork_round: two distinct committed checkpoints at one window end), executes once (exec_dup_round).

      Servers lane

      Teal area: servers whose log is not ⊥ at the end of the round (nonbot_logs). White line: useful servers, L ≠ ⊥ when the round began and not blocked in it (p. 19). Blue band hanging from n: servers blocked in the round. Dashed n/2: Lemma 2.2's precondition on useful servers (p. 11). Dashed ⌈3n/4⌉: Lemma 2.2's target for useful servers, and the sim's recovered-round floor on non-⊥ logs at window ends (SmrReport::recovered_round; not a paper threshold). The axis crops to n/2–n while every series stays there and says so under the lane name. r*: the recovered round, the first window end whose useful servers hold one executed sequence with no reset server and at least ⌈3n/4⌉ non-⊥ logs there and at every later window end; after a release the law card reads R = r* − release off it. Collapse and release mark a surge; the collapsed / recovering / recovered bands sit along the lane's bottom edge. Distinct logs are in the readout's useful hover.

      Resets · rollbacks

      Recovery only. Hollow amber ticks (top half): rounds with servers armed to reset, which roll back at the next window end. Filled red ticks (bottom half): window ends where servers rolled back to their checkpoint. The report counts servers and how many windows back, not the entries discarded; discarded entries are re-sent by their clients.

      Spread lane

      One curve per command: the share of useful servers whose log holds it at the round start, from delivery until one round after it is in every non-⊥ log (T_B + 1, the first round whose start shows the full share). Past that a checkpoint adoption can dip the share for a round; a curve without T_B ends at its peak, since holders fall to 0 once the entry commits. The spread drawer's median and band use the same cut. The header measures the whole run at its end (live: at the newest round): rounds from delivery to every log, median and 90th percentile, and the median as a multiple of log₂n; commands not in every log yet are counted apart as still spreading, so a surge cannot look faster than it was. A selected block's commands are drawn in a brighter teal, one selected command in white on top.

      Age vs T

      Live compact and recovery sessions only. Per round, the most rounds a log entry has waited since its stamp while sitting past a common prefix of the servers' executed part + log. Main line (and the readout): the contested prefix, shared by every non-⊥ server that disagrees with the reference somewhere; a server whose sequence is a strict prefix of the reference only lags (e.g. it just rejoined from a checkpoint and holds S + P for a round or two) and is left out. Faint line: the full prefix over every non-⊥ server, e5_probe's max_unsettled_age, which position fixed (T_E) reads. Red fill: the main line over T, an entry old enough to execute with its position still open; faint red ticks: rounds where only the full line is over T.

      Backlog lane

      Commands submitted and not yet committed (recovery: executed at the window end every useful server executed it; compact: every useful server executed it; extended: in every non-⊥ log, since it has no commit), at the end of each round, stacked by stage; the top line is the backlog. Each command is in exactly one stage, half-open intervals: client = injected, not delivered yet; being ordered = delivered, position not fixed yet (T_E: every non-⊥ log agrees on the prefix through it); ordered, waiting = position fixed, not yet frozen (recovery) or committed (compact); frozen in P = frozen at a window end and executed one window later. Freeze round = executed round − T; the newest P, not executed when the run ends, is read from its positions at its window end and the recovery rows' |P|. A command whose position is fixed only after a later stage began moves straight into that stage. Position fixed is recorded by live sessions only: a batch or loaded run merges ordering and waiting into one stage. Extended: client and spreading (delivered, not in every log yet).

      Block tiles and the life bracket

      Recovery: one tile per window end with its entries, average submit-to-commit latency and the smallest deadline margin (deadline − position fixed). Compact: one tile per T rounds, a display unit only, with the smallest deadline margin; its margins need the certificate feed, loaded once the block drawer opens. Rollback tiles commit nothing; drain is the first batch after a rollback. The selected block's life is a bracket above the tiles, from its first delivery to its execution, with the spread (median delivery → median every log) as a bar, then ticks at the median position fixed, the freeze (the tile's left edge) and the execution; a faint band behind the lanes spans the same rounds. The bracket shows faintly when a tile is hovered. Click a tile to open the block drawer; click it again or close the drawer to deselect the block and any command picked in it.

      Readout line

      One line for the round under the cursor: blocked share (during the round), useful servers (at its start), oldest unsettled age against T, the backlog with its stage split, committed (all at its end). Resets, rollbacks and recovery stragglers (executed lengths that differ across servers) appear only when present. Hovers name each value's instant and the related numbers: non-⊥ and distinct logs, stage counts and the oldest waiting command (2T is a recovery command's normal span), agreed prefix and executed range, and after the run the commands never committed: in flight, dead and, in extended, stranded (the client stopped after delivery and no server amplified it).

      Run summary

      The Summary tab of the right sidebar (next to Audit; it shows while no command is selected, every new selection switches to Audit, and a tab you pick yourself holds until the next selection), over the whole run or over the commands delivered inside the visible rounds. Spread: T_B per command (median, p90, still spreading). Latency by stage: median (bar) and p90 (tick) of the time committed commands spent in each backlog stage; batch and loaded runs have no position-fixed record, so ordering and waiting are one stage there. Commit margin: deadline − position fixed per committed entry, as on the tiles, with lines at 0 and T/4; live sessions only, from the committed sequence. Ordering: displacement = commit rank − submission rank among the commands in scope, where submission rank is the injection round and commands injected in the same round are tied (a command anywhere inside its round's group counts 0); the summary number is the share within ±3 places. Per-client FIFO: per client, commands must commit in issue (sn) order; a later command committed while an earlier one is not, or before it, is a violation; not applicable when no client issued two commands. Ordering and FIFO need the committed sequence (recovery: always loaded in live sessions; compact: once the block drawer has opened).

      Memory

      Live compact and recovery sessions only. Bytes are a structural estimate, not allocator RSS: element size × element count for every sequence (log entries, executed entries, P), maps charged at 1.5× their entries (per-client sequence numbers, §5 windows), the Merkle forest's peaks, nothing for allocator overhead or the stack. Per node is what one real server would hold: every structure the node references charged to it in full, as if it owned a private copy (its log and the median rule's index, its executed sequence and sn map, recovery's checkpoint S and P, its §5 certificate state wherever the lab keeps it); median and max over the servers whose log is not ⊥, with the median server's categories. The executed sequence stands in for the state machine's state, which is how the simulator represents it. Simulator: the wasm linear memory the page's engine holds (exact), and its node structures with every shared allocation (log chunks, executed chunks, interned checkpoints) charged once. Sharing = the standalone bytes of all n servers (⊥ ones included: they still hold their state and checkpoint) ÷ the simulator's node bytes for the same n servers, in the same units on both sides (elements physically held in a chunked sequence, maps for sn and §5 windows). The memory is read every round unless a read costs more than a tenth of a step; then less often, so the sparkline thins out. The readout warns from 1.5 GiB of wasm memory (wasm32 cannot exceed 4 GiB).

      Block entries tab

      Left: every entry the block committed, one row each (chain position, client, one mark); only rows near the view are built, ↑/↓ move the selection, a click selects the command everywhere. The mark shows the state that matters most: red, verified and no certificate constructible (only for commands the newest Verify covers: the clients it tracks, committed by its round); amber, slow: submit-to-commit latency above the run's p90, so about a tenth of the commands by construction; teal, a command you injected; grey, the rest. No-op and ⊥ entries are muted. Right: the selected entry's Merkle path or full tree, the proof steps and the certificates; with nothing selected, the forest's trees, those covering the block marked.

      Block order tab

      The block's commands from submission order (left, by injection round; tied commands kept in commit order so they never cross) to commit position (right). Lines are coloured by |displacement| (grey in place, blue 1–3, violet 4–9, amber 10+), the largest drawn on top and labelled; click a line to select its command everywhere, white on top. Beside it the block's displacement histogram and share within ±3, its per-client FIFO status and the run-wide number.
